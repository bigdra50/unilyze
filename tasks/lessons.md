# Lessons

## 2026-06-07: 委譲エージェントによるスコープ外ファイルの削除

- 事象: cursor-agent が「タスク成果物ではない」と判断して `.unilyze/refactor-before.json`（refactor-loop のベースライン）と `implementation-notes.html`（ルール必須の running ノート）を削除した
- ルール: 委譲プロンプトに「自分が作成していないファイルを削除しない。クリーンアップは行わない」を必ず含める。委譲後は git status で意図しない削除がないか確認する

## 2026-06-07: dirty working tree への委譲で未コミット成果が消失

- 事象: 未コミットのリファクタ（Round 3/4）が working tree にある状態で cursor-agent に別ファイルの作業を委譲したところ、エージェントが自分のスコープ外変更を「Cursor の暴走」と誤認し `git checkout` で破棄した。禁止事項に「削除禁止」を明記していても防げなかった（revert は削除ではないという解釈）
- ルール（多層防御）:
  1. グリーンになったラウンドは委譲前に必ず即コミットする（小さく頻繁なコミットの原則どおり）
  2. dirty tree からの委譲は Agent ツールの `isolation: "worktree"` を使い、隔離された worktree で実行させる
  3. 委譲プロンプトに「git checkout / restore / clean 等で既存変更を戻すことも禁止」と明記する

## 2026-06-07: パイプ経由の `gh pr edit --body-file -` で PR 本文を消失

- 事象: `gh pr view ... | sd ... | gh pr edit --body-file -` のパイプ中央の `sd` がバックグラウンドシェルで command not found になり、空 stdin が `--body-file -` に渡って PR 本文が空で上書きされた。バックグラウンドシェルはユーザープロファイルを完全には読まないため、Rust 製ツール（sd 等）が PATH にいない
- ルール（多層防御）:
  1. 破壊的コマンド（`gh pr edit` / `gh api PATCH` 等）へパイプで直接流し込まない。一旦一時ファイルに書き、非空・内容検証してから渡す
  2. バックグラウンド実行のコマンドチェーンでは Rust 製代替ツールを前提にしない（sed/awk 等 POSIX 標準にフォールバック）
  3. `&&` チェーンでも「前段が空出力で成功扱い」になるパイプ構成（cmd not found はパイプ全体を止めない）に注意する

## 2026-06-07: AskUserQuestion と結論提示の順序

- 事象: 推奨案のテキストと AskUserQuestion を同一ターンに出したところ、ユーザーには質問ダイアログだけが見えて結論が読めなかった（2回連続で中断された）
- ルール: 結論・推奨案はテキストのみのターンで完結に提示し、ターンを分けてから選択肢を聞く。長文+質問ツールを同一ターンに混ぜない

## 2026-06-10: 破壊的適用の前に生成物を検証する

- 事象: `gh issue edit --body-file` に渡すファイルを `sd` 経由のパイプで生成したが、`sd` が mise shim 故障で空出力となり、issue 本文2件を空で上書きした。
- ルール1: 上書き系コマンド（issue edit / file write / API PATCH）に渡す生成ファイルは、適用前に `wc -c` 等で非空・想定サイズを検証する。
- ルール2: パイプラインの中間ツールが正常動作するか（exit code / 出力有無）を、破壊的操作と同一コマンド内で混ぜない。生成→検証→適用を分離する。
- ルール3: 復元手段（原文の控え）があることを確認してから上書きする。今回は生成スクリプト内に原文があったため復元できた。

## 2026-06-11: サブエージェントの無出力待機は watchdog で死ぬ

- 事象: cursor-agent CLI を `2>/dev/null` で包んで完了をループ待機したラッパーエージェント4体が「600秒無進捗」の watchdog で強制終了した。実装自体は worktree に残っており、検証・報告だけが失われた。
- ルール1: 委譲プロンプトに「前景実行で進捗を逐次出力すること。長い無出力待機ループを作らないこと」を明記する。
- ルール2: ストール時は worktree の git status / diff から状態を再構成できる。調査系の所見だけはエージェント側に残るため、`agent --continue` の resume で回収する。
- ルール3: ストールしても成果物は無事なことが多い。再実行より先に worktree を確認する。

## 2026-06-11: 並行セッションと gh の認証競合

- 事象: 同一マシンに gh アカウントが2つ登録されており、並行セッションのアカウント切替と競合して GraphQL API が断続的に 401 を返した（REST は成功することが多い）。
- ルール1: `export GH_TOKEN=$(gh auth token --user <owner>)` でトークンを固定し、直後に `gh api user -q .login` で identity を検証してから書き込み操作を行う。
- ルール2: GraphQL 系（gh pr create/merge）が 401 を繰り返す場合は REST（gh api repos/.../pulls, PUT .../merge）に切り替える。
- ルール3: リトライは identity 検証付きループで行う（盲目リトライはしない）。

## 2026-06-11: マージパイプラインはテスト結果でゲートする / 和集合解消は意味検査が必要

- 事象1: 「テスト→commit→push→PR→merge」を1コマンドに連結した際、テスト1件失敗（801/802）でも後続が無条件実行されて赤のままマージした（PR #103）。
- ルール1: 連結パイプラインでは必ず `dotnet test ... || exit 1` 等で失敗時に後続を止める。目視確認に依存しない。
- 事象2: コンフリクトの機械的な和集合解消（両側保持）は、enum末尾のカンマ欠落・重複アサート（Equal(17)とEqual(20)の併存）・SARIF ルールIDの取り合い（UNI017衝突）という意味レベルの破綻を3種類生んだ。
- ルール2: 和集合解消の直後に必ず (a) ビルド (b) 全テスト (c) ID/連番系の重複チェック（rg で衝突候補を確認）を行い、green になるまで push しない。
- ルール3: 連番リソース（SARIFルールID等）を複数ブランチで並行採番させない。マネージャーが採番を事前に割り当てるか、マージ順を決めて後続に再採番を指示する。

## 2026-06-12: /tmp のファイルは Bash 呼び出しを跨いで生存保証がない

- 事象: PR 本文を /tmp に書き、後続の別 Bash 呼び出しで `-F body=@/tmp/...` 参照する構成が3回失敗した（macOS の /tmp 掃除・長時間セッション）。エラーは 2>/dev/null で握りつぶされ 401 と誤診した。
- ルール1: 生成ファイルとその消費は同一 Bash 呼び出し内で完結させる（mktemp → 使用 → rm）。
- ルール2: リトライループ内のエラーは握りつぶさず、種類（file not found / 401 / 422）を分岐表示する。

## 2026-06-12: push 成功を確認してから後片付けする / git 認証も identity 検証する

- 事象: 並行セッションの gh アカウント切替で git push が 403（別アカウントの credential が使われた）になったが、パイプラインが push の exit code を見ずに branch -D / worktree remove を実行し、未push コミットのブランチを削除した（reflog の hash 表示から復旧）。
- ルール1: `git push || exit 1` で push をゲートし、成功時のみ後片付けする。
- ルール2: push 直前にも identity を確認する（gh だけでなく git の credential も同一アカウント保証はない）。403 時は `credential.helper` 上書きで bigdra50 トークンを明示注入する。
- ルール3: 削除系の前に「リモートに存在するか」を git ls-remote で確認する習慣を徹底。

## 2026-06-12: テストハーネスは Release ビルドを優先する — 古い Release 残骸が偽の回帰を作る

- 事象: IncrementalAnalysisTests 等の E2E ハーネスが bin/Release を優先解決するため、過去の品質ゲート計測で残った古い Release DLL が新フラグ（--incremental）を知らず exit 1 → 12テストが一斉失敗。main の回帰と誤診しかけた（CI は Release 不在で Debug fallback のため green）。
- ルール1: ローカルで E2E が原因不明の一斉失敗をしたら、まず bin/Release の鮮度を確認（rm -rf bin/Release で Debug fallback に戻すのが最速）。
- ルール2: -c Release でゲート計測した後は Release 残骸が worktree に残ることを意識する。
