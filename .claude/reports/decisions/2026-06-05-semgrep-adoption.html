semgrepからunilyzeへ取り入れる機能の選定

Type: Decision Weight: heavy Date: 2026-06-05 Status: Proposed
← Index

結論

採用案: semgrepから「運用層・出力契約層」の設計を選択導入する。 第1弾は E (schemaVersion) → A (diff --fail-on) → B (StableFindingId + SARIF partialFingerprints) の順で着手する。
エンジン系の翻案（パターンマッチ・dataflow基盤）は採用しない。

理由

semgrepはルールがデータ (YAML)、unilyzeはルールがコード (C#のCalculator) という根本差があり、 エンジン・テスト記法の直輸入は動機となる制約がunilyze側に存在しない。 一方「CIゲート」「finding安定ID」「抑制コメント」「確度可視化」といった CLI解析ツールの運用層はそのまま課題が共通しており、ここに価値が集中する。

  • 19候補を抽出し、全件を「unilyzeの実コードを読んで反証を試みる」懐疑的検証にかけた結果、17件がadapt (形を直せば価値あり)、2件reject
  • E はCodeHealth重み調整 (文献根拠なしの独自重み付けで、将来チューニング予定) の前に入れないと過去trendが壊れるため最優先
  • A は DiffCalculator.cs:198-200 が劣化を計算済みなのに Program.cs:457,460 が常に return 0 という「配線のみで完成する」最大の即効候補
  • 優先順位はgpt-5.5と2ターン議論して決着 (E→A→B の並べ替え、ID契約のB内包化、ParameterTypes不採用)

適用範囲

unilyze本体 (bigdra50/unilyze) のロードマップ判断。 第1弾〜第3弾は製品機能、K (性能ベンチCI) はリポジトリ内部のCI投資としてロードマップ外管理。 L (到達不能コード検出) はexperimental smellsとして隔離しない限り保留。

課題 / コンテキスト

解決したい問題: unilyzeの次の開発方向を決めるにあたり、成熟した静的解析ツールであるsemgrep (LGPL 2.1のCE部分) から 移植・翻案できる設計を体系的に洗い出したい。

調査方法: semgrepコードベース5領域 (rules-config / scan-pipeline / output-ci / testing-qa / engine-core) と unilyze本体を計30エージェントで並列調査。 領域ごとに導入候補を抽出し、各候補を独立した懐疑的レビュアーがunilyzeの実コードと突合して adopt / adapt / reject 判定。最終優先順位はgpt-5.5とのLLM間議論 (2ターン) で確定。

制約: 1人開発の小規模OSS。ワークアイテムの粒度過多はオーバーヘッド。 CLIは手書き args ディスパッチ (Program.cs:4-26) で表面積を増やしにくい。 終了コードは 0/1 が公開契約 (Program.cs:173-176)。

第1弾の詳細スペック (検証済みの最小形)

E. schemaVersion 第1弾-1

整数定数 MetricsSchema.Version 1本をJSONに常時埋め込み。 CodeHealth重み・CycCC加算ルール・TypeId形式の変更で+1。

仕様
  • 旧JSON (版なし) はv0扱いで後方互換
  • diffで不一致なら SchemaMismatch フラグ + 警告1行
  • trendも混在検知時にstderr警告
見送り
  • 指標単位の自動比較除外 (対応表メンテが重い)
  • semver採用 (整数で足りる)
  • SARIFのtool.driver.versionとは混同しない (properties側に分離)

根拠: AnalysisResult.cs:6-14 に版なし / DiffCalculator.Compare は盲目比較

A. diff --fail-on 第1弾-2

--fail-on-degrade / --max-degraded N / --fail-on-new-critical / --audit を追加し、ゲート違反は exit 2。

仕様
  • DiffCalculatorが劣化を計算済み (DiffCalculator.cs:198-200)。配線のみで完成
  • exit 2 = quality gate failed に統一 (実行エラー1と区別)
  • GitHub Actionsサンプルをdocsに追加 (baseline解決は外部shellで例示)
  • E2E: 劣化→2 / --audit→0 / 新規Critical→2 / パースエラー→1
見送り
  • --baseline-ref (git worktree自動化) — 外部4行で代替可能、保留
  • semgrep流5値exit code表・欠番予約 — 過剰

根拠: Program.cs:457,460 が常に return 0

B. StableFindingId + SARIF fingerprints 第1弾-3

TypeId + Kind + MethodName + ParameterCount のSHA256を unilyzeSmellHash/1 としてSARIF partialFingerprintsへ出力。

仕様
  • コード本文・メッセージ・行番号はhashに含めない (微変更でIDが割れる事故を防ぐ)
  • StableFindingId 型として切り出し、CのID語彙・SARIF ruleIdと同一の公開契約に
  • ID契約のdocsも同じPRで公開 (独立ワークアイテムにはしない)
  • 付随: diffの型リネーム耐性化 (unmatched同士をシグネチャ集合のJaccard類似度でフォールバック照合)
見送り
  • ParameterTypes — 型リネームで割れる方が実害大 (gpt-5.5と合意)
  • 正規化スニペットhash — 安定IDの目的と逆行
  • BloomFilter128流用 — 弱ハッシュで不適、SHA256を使う

根拠: SarifFormatter.cs:113-134 にfingerprintなし → Code Scanningで行ズレ重複が発生する構造

第2弾・第3弾の詳細

C. インライン抑制コメント // unilyze-ignore: <id>第2弾

型/メソッド宣言の同一行末尾または直前行の単独コメントで該当findingを抑制。 エージェントの「ここは意図的に複雑」判断をコードに恒久記録し、refactor-loopの収束ノイズを構造的に除去する。

  • ID語彙はBで確立する StableFindingId 契約の完全一致のみ。サフィックス一致は不採用 (unilyzeのIDはフラット16種)
  • 裸の // unilyze-ignore (ID無し) は不採用 — god-class狙いの抑制がboxingまで消す事故を防ぐ
  • 未知IDはstderr警告。抑制済みは出力から単に除外 (--show-suppressed は将来拡張)
  • 実装フックは AnalysisPipeline.cs:357-416 — 型宣言ノードとSemanticModelが手元にありtrivia走査が容易。CodeSmellDetectorには手を入れない
  • スキル側docs (blind-spots.md / refactor-loop) を「合意済み箇所は1度コメントで恒久化」運用に更新
D. 解析確度 (confidence) の型単位出力第2弾

SemanticModel例外時のsilentフォールバック (AnalysisPipeline.cs:332-339) と DITの0/1概算 (:341-352) を TypeMetrics に記録し可視化する。

  • 「semanticが使えたか / catchフォールバックしたか / DIT概算か」のbool数個から開始 (指標×3値の全付与は過剰)
  • statuslineに「N型がapprox」の1行サマリ
  • 命名はdiffの「degraded」(メトリクス悪化の意味で予約済み) と衝突させず confidence 系を使う
  • HTML色分け・終了コード連動は次フェーズ
  • 付随バグ: Program.cs:266 のschema説明が "SyntaxOnly" or "Semantic" のままで実装の4値enumと不一致 (別issue)
  • 注意: 元提案の動機「refactor-loopが誤収束」は不成立 — 収束判定のCodeHealthは全構成要素が構文解析でexact
I. 生成コード除外 (excludeGlobs)第2弾

*.g.cs 等のグロブ除外設定を excludeDirs と同系統で追加。 blind-spots.md:9 が認めている実在ギャップへの直接対処。

  • gitignoreフィルタはopt-in (--respect-gitignore、既定off) — 既定onだと未コミットの新規.csが無言で消える
  • 元提案の git ls-files ターゲット選択差し替えは不採用 — 解析は既にAssets/配下スコープ (ProgramHelpers.cs:99-106) でPackageCache混入は起きず、ボトルネックも列挙ではなくSemanticModel構築
G. JSONゴールデンスナップショットテスト (Verify)第3弾
  • VerifyXunitのreceived/verifiedフローでJSONから段階導入。価値が出たらSARIF/statusline追加
  • ノーマライザ必須: AnalysisPipeline.cs:80 のUtcNow、SarifFormatter.cs:82 の絶対URIを固定トークン化。Windows対応時のパス差検出器を兼ねる
  • HTMLフルスナップは不採用 — 静的テンプレ2398行+JSON注入なのでJSONスナップで実質カバー
  • 現状の構造アサーション型テストはCodeHealth重み定数の変更をすり抜けうる、という穴への対処
F. 実UnityリポジトリQAコーパス (release時のみ)第3弾
  • tests/qa/repos.json (url + 固定SHA + xfail理由 + expectedLevel) を定義
  • シードはcross-validationで選定済みの BossRoom / HelloMarioFramework / UniTask / VContainer / unilyze-self + Zenject系1つ
  • release時に --depth=1 clone → 完走 + exit 0 + 未処理例外なし + analysisLevelが想定以上、を検証
  • graceful degradation (NullableWalker NRE catch等) は実リポジトリでしか踏みにくいのに現状E2Eは合成フィクスチャのみ (CliE2eTests.cs:92-160)
  • unilyze qa サブコマンド新設はしない (CLI表面積を増やさない)。通常CIのnet8/9/10マトリクスにも入れない
J. --require-level / H. --jobs第3弾
  • J: 到達解析レベルが要求未満なら出力は通常通り出した上で exit 2。「CIが知らないうちにSyntaxOnlyで回っていた」事故の検知。逆側の --suppress-analysis-errors は不採用 (unilyzeは既に常にexit 0の最大fail-open)
  • H: --jobs <n> と maxJobs 設定による手動上書きのみ。3箇所のParallelに共通ParallelOptionsを渡す。cgroup自前読み・0.85係数は不採用 — .NETランタイムが既にcgroup-aware (semgrepが自作するのはOCamlにランタイム支援がないから)

保留・却下した候補

K. 解析性能ベンチ回帰CI 内部投資扱い

BenchmarkDotNet別プロジェクト + CIでbase/head 2点比較。

保留理由
  • 元提案の「既存統計出力から所要時間取得」は事実誤認 (Stopwatch計装が一切ない)
  • 製品価値でなく開発運用 — 公開ロードマップから外し内部品質投資として別管理
  • 製品CLIに計時APIは入れない (gh pr comment相当もCLIに実装しない)
L. ConstantCondition / UnreachableCode 検出器 保留

Roslyn AnalyzeControlFlow / GetConstantValue の薄いラッパで新CodeSmellKind 2種。

保留理由
  • メトリクス+改善検証ツールからlinterへの軸ずれ (gpt-5.5判定: experimental smellsとして隔離しない限り保留)
  • 採用する場合のゲートはFullEngine限定でなくCoreEngine以上 (既存検出器の慣行)、#if UNITY_EDITOR偽陽性対策が必須、dead storeは別タスク
// ruleid: 式ゴールデンアノテーション 却下

semgrep流: テストコードにアノテーションを書き期待findingを宣言する方式。

却下理由
  • semgrepがこの方式を取るのは「ルールがYAMLデータでホスト言語のユニットテストからimportできない」制約への回避策
  • unilyzeのメトリクスは普通のC#関数で、既に638個の Assert.Equal がゴールデン値をピン留め済み。移植動機となる制約が存在しない
  • unilyze test サブコマンドはテストランナーのCLI同梱で役割逸脱
不動点ワークリスト共通基盤の先行導入 却下

将来のメソッド内フロー解析に備えたCFG上の有界不動点ヘルパ。

却下理由
  • 消費者となる機能がゼロのYAGNI (前提となるL自体が保留)
  • unilyzeは純粋に構文ベース — CFG/dataflowパラダイムが完全に不在で、使うメトリクス未確定のまま持ち込むのは負債
  • 「有界反復」の思想は RankCalculator.cs:73-106 のpower iteration (MaxIterations=100 + 収束閾値) として採用済み

LLM間議論の決着点 (gpt-5.5 / copilot、2ターン)

論点結論
第1弾の順序 A→E→B から E→A→B へ並べ替え。EはJSON/diff/trend/エージェント契約すべての土台のため最初に固定
exit code 2 の意味 A/Jで分けず「quality gate failed」に統一。詳細理由はstderr/JSONへ
安定finding ID契約の扱い 独立ワークアイテム化せずBの実装内で StableFindingId として切り出し (1人開発でアイテム粒度過多は逆効果)。契約化は必須、ワークアイテム化は不要
fingerprint入力 ParameterCountまで。ParameterTypesは型リネーム/namespace移動/using整理で割れやすくbaseline/ignore用途でノイズ。同名同数別型overloadの衝突は許容できる低頻度リスク
analyze --baseline 現段階では diff の糖衣。Aの失敗判定基盤が固まるまでdocsレベルの運用例に留める
L / K の扱い Lはlinter領域への越境で捨て寄り保留。Kは内部品質投資扱いで公開ロードマップ外
